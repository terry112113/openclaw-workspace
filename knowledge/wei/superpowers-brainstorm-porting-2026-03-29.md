## 一、brainstorm 核心设计解析

### 1.1 技能架构（YAML frontmatter）

```yaml
---
name: brainstorming
description: "You MUST use this before any creative work..."
---
```

### 1.2 核心流程（9步检查清单）

```
探索项目上下文
    ↓
有无视觉问题？→ 提供 Visual Companion（独立消息）
    ↓
逐一提问澄清（一次一问）
    ↓
提出 2-3 种方案（含权衡+推荐）
    ↓
分段展示设计 → 用户逐段批准
    ↓
撰写设计文档 → 保存至 docs/superpowers/specs/
    ↓
Spec 自我审查（占位符/一致性/范围/歧义）
    ↓
用户审查设计文档（用户 gate）
    ↓
调用 writing-plans 技能（唯一出口）
```

### 1.3 关键设计原则

| 原则 | 说明 |
|------|------|
| **HARD-GATE** | 在设计批准前，绝不写代码、不触发实现技能 |
| **一次一问** | 不一次性抛出多个问题，逐个击破 |
| **多方案权衡** | 必须提出 2-3 种方案，含各自权衡和推荐 |
| **分段展示** | 设计按复杂度分段展示，每段后确认 |
| **双重审查** | AI 自我审查 + 用户审查 gate |
| **YAGNI** | 坚决剔除未请求的功能 |

### 1.4 两阶段 review

- **阶段一（Spec Self-Review）：** AI 写完 spec 后自检占位符、内在一致性、范围、歧义
- **阶段二（User Review Gate）：** 用户阅读 spec 并批准后才能进入实现

### 1.5 原子化任务（writing-plans 继承）

- 每步 2-5 分钟
- 每步有精确文件路径、完整代码、验证步骤
- RED-GREEN-REFACTOR 循环（TDD）

## 二、三司会审现状分析

### 2.1 当前流程

```
太上皇提出问题/任务
    ↓
狄仁杰主持
    ↓
李元芳（都察院御史）→ 深度研究、监察
宋慈（刑部尚书）→ 快速执行、审判
    ↓
双方辩论（目前较为随意）
    ↓
狄仁杰审核总结
    ↓
汇报太上皇
```

### 2.2 缺失的关键环节

1. **无强制设计阶段**：讨论后直接进入执行，缺少"设计文档化"步骤
2. **无分段确认**：李元芳和宋慈的方案是一次性呈现，而非分段逐步确认
3. **无多方案探索**：往往只给出一个方案，缺少 2-3 方案的权衡比较
4. **无自我审查**：方案产出后缺少 AI 自检流程
5. **无原子化任务拆分**：执行阶段颗粒度不明确

## 三、移植方案：三司会审 × brainstorm

### 3.1 整体映射

| superpowers brainstorm | 三司会审映射 |
|----------------------|-------------|
| 用户提问 | 太上皇提出任务/目标 |
| 探索项目上下文 | 李元芳调查现场、宋慈了解案情 |
| 逐一提问澄清 | 狄仁杰向双方追问（一次一问） |
| 提出 2-3 方案 | 李元芳与宋慈各陈己见，狄仁杰归纳多方案 |
| 分段展示设计 | 狄仁杰逐段宣布裁定（ Architecture → 细节 → 风险） |
| Spec 自我审查 | 宋慈（刑部）进行 self-review，检视一致性/遗漏 |
| 用户审查 gate | 太上皇御览裁可 |
| 调用 writing-plans | 宋慈制定执行计划（原子化任务清单） |

### 3.2 新增：三司会审 Brainstorm SKILL.md

路径：`skills/三司会审-brainstorm/SKILL.md`

```yaml
---
name: 三司会审-brainstorm
description: "三司会审讨论阶段专用技能。议题提出后，必须先经讨论、探索、方案比较、狄仁杰分段陈述、太上皇御可，方可进入执行阶段。"
trigger: 当太上皇提出新的任务、问题或议题时激活
exit_skill: 三司会审-writing-plans（唯一出口）
---
```

### 3.3 三司会审 Brainstorm 流程（9步）

```
【第一步：调查现场】
李元芳探索上下文（查文件、git历史、相关文档）
宋慈整理已知信息（快速摘要）
狄仁杰宣布议题范围

【第二步：狄仁杰提议视觉辅助】（如涉及UI/架构图）
独立消息："案情或可图示，是否需要展示相关图示？"

【第三步：一次一问澄清】
狄仁杰向李元芳/宋慈逐一追问
- 目的为何？约束条件？成功标准？
- 每次只问一个问题

【第四步：多方案陈述】
李元芳陈述方案A（含权衡）
宋慈陈述方案B（含权衡）
（如需要）狄仁杰提出方案C
狄仁杰给出推荐并说明理由

【第五步：狄仁杰分段陈述裁定】（分段确认）
- 第一段：总体架构/方向 → "此节是否妥当？"
- 第二段：执行路径/关键节点 → "此节是否妥当？"
- 第三段：风险/边界情况 → "此节是否妥当？"
每段后等待反馈，必要时修订

【第六步：宋慈撰写"审议纪要"】
路径：docs/三司会审/specs/YYYY-MM-DD-<议题>-审议纪要.md
包含：问题陈述、多方案权衡、选定方案、分段设计

【第七步：宋慈自我审查】
检查项：
□ 是否有占位符（TBD/TODO/未决）？
□ 方案内部是否矛盾？
□ 范围是否适中（太宽？太窄？）？
□ 是否有歧义可导致理解偏差？
发现问题立即修正

【第八步：太上皇御览】
"审议纪要已拟定。请太上皇御览，有何更改指示？"
等待御可。御可不通过 → 返回第六步修订

【第九步：进入执行】
狄仁杰宣布："方案已定。" 调用"三司会审-writing-plans"技能
（唯一出口，不得直接进入实现）
```

### 3.4 关键差异：原版 vs 三司会审版

| 维度 | superpowers 原版 | 三司会审版 |
|------|-----------------|-----------|
| 角色 | AI 单agent | 狄仁杰+李元芳+宋慈三人 |
| 提问方 | AI 向用户提问 | 狄仁杰向李元芳/宋慈提问 |
| 方案来源 | AI 提出 2-3 方案 | 李元芳+宋慈各陈己见，狄仁杰综合 |
| 自我审查 | AI self-review | 宋慈（刑部尚书）执行审查 |
| 最终 gate | 用户批准 | 太上皇御可 |
| 出口 | writing-plans skill | 三司会审-writing-plans |

## 四、关键设计原则（刻入三司会审 Brainstorm）

### 4.1 强制两阶段审查

```
议题 → 讨论 → 审议纪要
    ↓
[阶段一] 宋慈 self-review（一致性/完整性/歧义）
    ↓
[阶段二] 太上皇御览 gate
    ↓
御可 → 才可进入执行
```

### 4.2 HARD-GATE（刻入狄仁杰）

> **狄仁杰内心铭文：**
> "未得御可，不得擅动。无论案情多简单，未经讨论不得直接执行。"
> "Simple 项目更需审查——未审视的假设是最大的浪费。"

### 4.3 原子化任务继承（传递给 writing-plans）

brainstorm 的输出（审议纪要）将直接交由 writing-plans 阶段：
- 宋慈负责将每项裁定拆解为 2-5 分钟的原子步骤
- 每步含精确文件路径、完整操作、验证方法
- 全程遵循 TDD（先定测试，再实现）
