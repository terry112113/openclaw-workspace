## 一、熔断触发条件

### 1.1 基础触发规则

**核心指标：连续失败次数（Consecutive Failures）**

```
熔断状态机：
  正常运行 → 连续失败3次 → 熔断开启
  熔断中 → 冷却时间到期 → 试运行（1次）
  试运行成功 → 恢复正常
  试运行失败 → 继续熔断（冷却时间×2）
  熔断累计3次未恢复 → 触发狄仁杰告警
```

### 1.2 具体触发阈值

| 场景 | 触发条件 | 熔断持续时间 |
|------|---------|------------|
| 任务执行异常 | 连续失败 **3次** | 15分钟 |
| 任务超时 | 连续超时 **3次** | 15分钟 |
| 资源耗尽 | 检测到内存/CPU > 90% | 30分钟 |
| 外部依赖不可用 | API返回5xx **2次** | 30分钟 |
| 人工触发 | 狄仁杰或魏征手动熔断 | 手动恢复 |

### 1.3 失败类型定义

- **执行失败**：任务抛异常或返回error状态
- **超时失败**：执行时间超过预设阈值的2倍
- **资源失败**：因系统资源不足被操作系统Kill
- **依赖失败**：外部依赖（API/DB）不可达或返回错误

## 二、熔断阈值设计

### 2.1 方案选择：独立阈值 + 全局兜底

**推荐方案：混合模式**

```
┌─────────────────────────────────────────────────┐
│              全局熔断兜底（最后防线）              │
│  ┌──────────────────────────────────────────┐   │
│  │         单个Cron任务独立阈值              │   │
│  │  ┌────────┐ ┌────────┐ ┌────────┐        │   │
│  │  │ cron_A │ │ cron_B │ │ cron_C │ ...    │   │
│  │  │  3次   │ │  5次   │ │  2次   │        │   │
│  │  └────────┘ └────────┘ └────────┘        │   │
│  └──────────────────────────────────────────┘   │
└─────────────────────────────────────────────────┘
```

### 2.2 独立阈值配置

每个cron任务可配置独立阈值，默认值如下：

| 任务类型 | 默认熔断阈值 | 熔断时长 | 说明 |
|---------|------------|---------|------|
| 关键任务（数据备份、核心同步） | 2次 | 15分钟 | 高敏感，宁可错熔不可漏 |
| 标准任务（信息拉取、报表生成） | 3次 | 30分钟 | 默认配置 |
| 低敏感任务（日志清理、非核心） | 5次 | 60分钟 | 允许更多重试 |
| 外部依赖任务（API调用） | 2次 | 15分钟 | 外部服务不稳定 |

### 2.3 全局阈值（兜底机制）

```
全局熔断触发条件：
- 任意 5 个不同的cron任务同时进入熔断状态
- 或 任意 1 个任务在 1 小时内熔断 3 次（不含恢复）
- 触发全局熔断：暂停所有非关键cron任务
```

**全局熔断恢复条件**：
- 至少 3 个任务成功执行
- 或 人工确认外部依赖恢复正常
- 或 狄仁杰手动解除

## 三、降级策略

### 3.1 降级方案选择

| 方案 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **进入队列等待** | 数据同步类任务 | 不丢数据 | 积压风险 |
| **立即丢弃（标记跳过）** | 非关键任务 | 快速恢复 | 可能丢数据 |
| **降频执行** | 周期性任务 | 平衡风险与频率 | 配置复杂 |
| **人工介入** | 高风险任务 | 最安全 | 人工成本高 |

### 3.2 推荐降级策略

**根据任务优先级选择**：

```
P0 关键任务（备份、核心同步）：
  熔断 → 进入优先级队列 → 熔断恢复后立即执行
  
P1 标准任务（信息拉取、报表）：
  熔断 → 进入普通队列 → 熔断恢复后按序执行
  队列满（>100条）→ 丢弃最旧的
  
P2 低敏感任务（日志清理）：
  熔断 → 丢弃（直接跳过，不排队）
  
P3 例行任务（健康检查）：
  熔断 → 丢弃 + 记录日志
```

### 3.3 队列设计

**队列配置**：
```yaml
queue:
  max_size: 100        # 队列最大容量
  ttl: 3600           # 队列中任务保活时间（秒）
  retry_interval: 300 # 队列重试间隔（秒）
```

**队列监控指标**：
- 队列长度
- 队列积压时间（ oldest_item_age ）
- 队列丢弃率

## 四、告警链设计

### 4.1 告警分级

```
┌─────────────────────────────────────────────────┐
│  告警L1：任务级告警                               │
│  触发：单个任务连续失败2次                        │
│  通知：魏征（执行者）                             │
│  渠道：飞书私信 + 日志                            │
│                                                  │
│  告警L2：熔断告警                                 │
│  触发：任务进入熔断状态                            │
│  通知：魏征 + 狄仁杰                              │
│  渠道：飞书群消息（@wei @di）                    │
│                                                  │
│  告警L3：持续熔断告警（需狄仁杰介入）              │
│  触发：同一任务熔断3次仍未恢复                     │
│  通知：狄仁杰（必须）                             │
│  渠道：飞书群（加急）+ 触发三司会审                │
│                                                  │
│  告警L4：全局熔断告警（系统级）                    │
│  触发：全局熔断条件达成                            │
│  通知：狄仁杰 + 李元芳 + 魏征                     │
│  渠道：飞书群全员通知 + 电话（如配置）             │
└─────────────────────────────────────────────────┘
```

### 4.2 告警消息模板

**L2 熔断告警**：
```
【熔断通知】@di @wei
■ 任务：[cron任务名]
■ 熔断原因：连续失败3次
■ 最后错误：[简要错误信息]
■ 熔断时长：15分钟
■ 当前队列状态：[长度/积压时间]
■ 建议操作：[查看日志/人工介入/等待恢复]
```

**L3 持续熔断告警**：
```
[急] @di
【持续熔断·需裁决】
■ 任务：[cron任务名] 已在1小时内熔断3次
■ 错误模式：[是否相同错误]
■ 影响范围：[业务影响]
■ 已尝试：[解决措施]
■ 建议：[恢复/修改阈值/永久禁用]
■ 请狄仁杰裁决下一步行动
```

### 4.3 告警抑制（防轰炸）

```
规则：
- 同一任务在 5 分钟内的告警合并为 1 条
- 告警L1 在 L2 触发后自动抑制
- 全局熔断期间，任务级告警降频发送（每30分钟1次）
```

## 六、配置示例

### 6.1 cron任务配置示例

```yaml
cron_tasks:
  backup_database:
    name: "数据库每日备份"
    threshold: 2          # 独立阈值：连续失败2次熔断
    breaker_duration: 900  # 熔断15分钟
    priority: P0
    degradation: "queue"   # 降级策略：进入队列
    
  sync_user_data:
    name: "用户数据同步"
    threshold: 3
    breaker_duration: 1800
    priority: P1
    degradation: "queue"
    
  cleanup_logs:
    name: "日志清理"
    threshold: 5
    breaker_duration: 3600
    priority: P2
    degradation: "discard"  # 降级策略：直接丢弃
    
  health_check:
    name: "健康检查"
    threshold: 3
    breaker_duration: 900
    priority: P3
    degradation: "discard"

global:
  max_breakers: 5          # 全局熔断阈值
  recovery_check_interval: 60  # 恢复检查间隔（秒）
```

## 七、监控与可观测性

### 7.1 关键指标

| 指标 | 说明 | 告警阈值 |
|------|------|---------|
| `cron.breaker.active` | 当前熔断中的任务数 | > 0 |
| `cron.breaker.total` | 累计熔断次数 | 无 |
| `cron.task.failure_rate` | 任务失败率 | > 20% |
| `cron.queue.size` | 当前队列长度 | > 80 |
| `cron.queue.oldest_age` | 队列最旧任务等待时间 | > 3600s |

### 7.2 日志规范

```
熔断事件日志格式：
[BREAKER] timestamp=YYYY-MM-DD HH:mm:ss task={task_name} event={opened|closed|half_open} consecutive_failures={n} duration={seconds}

降级事件日志格式：
[DEGRADE] timestamp=YYYY-MM-DD HH:mm:ss task={task_name} action={queued|discarded} queue_size={n}
```

## 八、附录

### 8.1 FAQ

**Q：熔断期间任务数据会丢失吗？**
A：配置 `degradation: queue` 的任务会进入队列，不会丢失；配置 `discard` 的任务会被丢弃。

**Q：如何手动恢复熔断？**
A：通过 OpenClaw 工具手动执行恢复命令，狄仁杰或魏征有权限。

**Q：熔断恢复后任务会立即执行吗？**
A：会进入"试运行"状态，成功则恢复正常，失败则继续熔断。
